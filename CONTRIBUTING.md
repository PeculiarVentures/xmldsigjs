# Contributing to xmldsigjs

Thank you for your interest in contributing to `xmldsigjs`! This document describes how to set up the project, which checks a change must pass, and how releases are made.

## Development Setup

### Prerequisites

- Node.js `^20.19.0 || >=22.12.0` (CI uses Node.js 24)
- npm (the repository is an npm workspace locked with `package-lock.json`)

### Installation

```bash
git clone https://github.com/PeculiarVentures/xmldsigjs.git
cd xmldsigjs
npm ci
npm test
npm run build
```

## Project Layout

- `packages/core/` is `xml-core`: the `XmlObject` base class, the `@XmlElement`/`@XmlChildElement`/`@XmlAttribute` decorators, `Convert`, and `setNodeDependencies` for `@xmldom/xmldom` and `xpath` in Node.js.
- `packages/xmldsig/` is `xmldsigjs`: XML Digital Signature (`SignedXml`, algorithms, transforms, `Application.setEngine`).
- `packages/xades/` is `xadesjs`: XAdES on top of xmldsigjs.
- `packages/<name>/src/index.ts` is the package's only public entry point and must stay aligned with its `exports`.
- `packages/<name>/test/` holds test support code only: `config.ts` (registers `@xmldom/xmldom`, `xpath` and a WebCrypto engine) and XML fixtures in `packages/xmldsig/test/static/`.
- `tsdown.config.ts` at the repository root builds every package (tsdown `workspace` mode). There are no per-package build configs.
- `tsconfig.json` at the root is used for typechecking, tests and the declaration build. Its `paths` map `xml-core`, `xmldsigjs` and `xadesjs` to their `src`, so packages and tests use the sibling sources without building them first.
- `packages/<name>/build/` is generated by `npm run build` and is not committed.

## Development Workflow

### Code Quality

Before opening a pull request, run from the repository root:

```bash
npm run lint          # oxlint
npm run format:check  # oxfmt
npm run typecheck     # tsc --noEmit
npm test              # vitest, runs once and exits
npm run build         # tsdown, also checks every package with attw
```

Fix lint and formatting issues with `npm run lint:fix` and `npm run format`. Use `npm run coverage` to produce a coverage report, and `npx vitest run packages/<name>` to run one package's tests.

### Testing

- Use Vitest and import `describe`, `it` and `assert`/`expect` from `vitest` (globals are off).
- Put tests next to the code they cover as `*.spec.ts` in `packages/<name>/src/`. Suites about `SignedXml` are named `signed_xml.<topic>.spec.ts`; `signed_xml.compat.spec.ts` also verifies with `xmlsec1` when it is installed.
- Import `../test/config.js` (relative to the spec) to register the XML dependencies and the WebCrypto engine.
- Cover new behavior and bug fixes with tests. For signature changes, sign and verify, or verify a fixture with a known result.
- Keep tests deterministic: no network access or external services.

### Build And Package Exports

Every package is ESM-only; there is no CommonJS build, and CommonJS consumers load it through `require(esm)`. tsdown builds `src/index.ts` into `build/index.js` with `.d.ts` declarations. Output is unbundled, so every source module is emitted under `build/` mirroring `src/`, but only the root entry is reachable through `exports`. The syntax target comes from `engines.node`; do not set `target` in `tsdown.config.ts`.

`exports` and the legacy `main`/`module`/`types` fields in each `packages/<name>/package.json` are generated by tsdown on every build and must not be edited by hand. CI fails if the build changes a `package.json`.

Use named exports only (no `export default`) and no top-level `await`, so `require()` of the packages keeps working on supported Node.js versions. Use `import type` for type-only imports, including classes that are only used as types (`verbatimModuleSyntax` keeps every other import, and an unneeded import can create a load-order cycle). Because the output is unbundled, a module must not extend or call a class from a module that imports it back at load time.

`useDefineForClassFields` is `false`: the xml-core decorators install accessors on the prototype, and class field definitions would shadow them.

Every package has `"sideEffects": false`. The default algorithms and transforms are registered in the same modules that export their registries, so bundlers keep them whenever `SignedXml` or `CryptoConfig` is used. Don't add code that only works because some other module was imported for its side effects.

### Dependencies

- `xml-core` is a **peer** dependency (and a dev dependency) of xmldsigjs and xadesjs, and `xmldsigjs` of xadesjs: `setNodeDependencies`, the decorator schemas, `Application.setEngine` and the algorithm and transform registries are module-level state, so an app must have only one copy.
- `pkijs` and `asn1js` are **peer** dependencies of xmldsigjs; pkijs checks asn1js objects with `instanceof`.
- `@xmldom/xmldom` and `xpath` are **peer** dependencies of xml-core, which receives them through `setNodeDependencies`.
- `@peculiar/utils` is a regular dependency. Use its root or subpath entries (`/bytes`, `/encoding`), never `/legacy`.
- The internal `xml-core`/`xmldsigjs` ranges are bumped by the release pull request; don't change them by hand.

### Commit Messages

Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). Pull requests are squash-merged, so the pull request title becomes the commit message and must follow the same format.

```plain
type(scope): description

[optional body]

[optional footer]
```

Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `style`, `revert`. Use `core`, `xmldsig` or `xades` as the scope for package-specific changes (for example `fix(xades): ...`).

Mark breaking changes with `!` after the type or scope (for example `feat(core)!: ...`) and/or a `BREAKING CHANGE:` footer.

### Pull Requests

1. Fork the repository and create a branch from `master`.
2. Make your changes, with tests.
3. Run the checks listed above.
4. Open a pull request with a Conventional Commit title.

## Code Style

- Write TypeScript.
- Follow the oxlint (`.oxlintrc.json`) and oxfmt (`.oxfmtrc.json`) configuration. Prefer fixing the source over adding rules that only create churn, and disable a rule only when it fights the established style.
- Keep changes small and localized to the owning package.
- Prefer `BufferSource`-based public APIs over Node.js-specific `Buffer` types.
- Keep public exports stable; breaking changes need a major release.

## Releases

Releases are managed by [release-please](https://github.com/googleapis/release-please) (`release-please-config.json`, `.release-please-manifest.json`). xml-core, xmldsigjs and xadesjs share one version and are released together.

1. On every push to `master`, the **Release** workflow first runs lint, format, typecheck, tests, and build (the **Test** workflow). Only when they pass does release-please open or update a `chore(release): vX.Y.Z` pull request. It bumps the root and every `packages/*/package.json` version, the internal `xml-core`/`xmldsigjs` ranges, and `package-lock.json`. The version comes from the commits: a breaking change bumps major, `feat` bumps minor, and `fix`, `perf`, `build`, and `revert` bump patch. Other types do not trigger a release. Any releasable commit releases all three packages.
2. Merge the release pull request. release-please creates one `vX.Y.Z` tag and one GitHub Release with the notes from the pull request; the workflow then publishes every package whose version is not on npm yet via Trusted Publisher, with provenance, dependencies first, and moves the major tag (for example `v3`) when this is the newest release of that major.

To retry a failed or partial npm publish, run **Release** manually from the `vX.Y.Z` tag; packages already on npm are skipped. Set the optional `RELEASE_TOKEN` secret (PAT or GitHub App token) so the Test workflow runs on the release pull request. Every package needs an npm Trusted Publisher for this repository, workflow `release.yml` and environment `npm`.

Releases up to xml-core 1.2.6, xmldsigjs 2.8.8 and xadesjs 2.6.8 were published by hand with `<package>@<version>` tags; `bootstrap-sha` in `release-please-config.json` marks where release-please starts.

Release notes live only in [GitHub Releases](https://github.com/PeculiarVentures/xmldsigjs/releases); there is no `CHANGELOG.md`. Only `feat`, `fix`, `perf`, `build`, `revert`, and breaking changes are listed. Force a version with a `Release-As: x.y.z` line in a commit body. To fix the notes for a merged change, add a `BEGIN_COMMIT_OVERRIDE` … `END_COMMIT_OVERRIDE` block with the corrected commit message to that pull request's description; edits to the release pull request description are overwritten when new commits land.
